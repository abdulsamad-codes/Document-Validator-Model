# Project Context – FinTech Document Verification System

Last updated: 2026-08-15. This file is the single source of truth for project state across sessions/tools — keep it current rather than trusting an earlier assistant summary in chat history.

## What this project is

A full-stack system for banks/KPITB to onboard merchants: upload financial onboarding documents, run them through OCR → field extraction → confidence scoring → normalization → a business-rule engine → human review, and curate corrected data into a versioned dataset for continuous learning. Backend: FastAPI + PostgreSQL (SQLAlchemy 2 + Alembic). Frontend: React 19 + Vite.

**⚠️ The GitHub repo (`abdulsamad-codes/Document-Validator-Model`) is public.** Real onboarding documents (real IBANs, CNICs, officer names) belong in `Confidential Data/` at the project root, which is gitignored — never loose in the repo. On 2026-08-13 a real onboarding PDF was found committed and pushed un-ignored (fixed by untracking + gitignoring it, commit `bc57cff`); git history was deliberately left as-is rather than rewritten, so that one file is still recoverable from an old commit if anyone goes looking. See `Confidential Data/` for the ~19 real documents already handled correctly.

**⚠️ Never run `pytest` while real data is loaded in the dev database.** `tests/conftest.py`'s autouse `isolated_database` fixture runs `DELETE FROM applications` (cascading to documents/queue_jobs) before AND after **every single test**, against whatever database `SessionLocal`/`DATABASE_URL` points at — which locally is the same Postgres database the running backend and queue worker use. On 2026-08-13 this wiped a real uploaded application while it was mid-processing (see below). Before running the suite locally, check the `applications` table is empty first, or point `DATABASE_URL` at a separate test database. (Independently confirmed by a parallel session working on `feature/zarghuna-bulk-queue`: a 10-minute full-suite run wiped all users mid-run, breaking login until reseeded — same root cause.)

### 2026-08-13 stabilization session (this session)

A prior session (different tool) had merged everything but left the suite at "89 failing tests, never root-caused," and had introduced a rule-registry regression while trying to fix an unrelated test. This session found and fixed the real causes:

- **Missing migration**: `DocumentType.BULK_UPLOAD` existed in Python but was never added to the Postgres enum — every bulk upload failed. Added `alembic/versions/02ffa030b9e1_add_bulk_upload_document_type.py`.
- **Wrong repository method call**: `upload_bulk` called a nonexistent `QueueJobRepository.enqueue()`; fixed to call the real `enqueue_uploaded_documents(...)`, removed a dead import, rewrote the stale docstring.
- **Real atomicity bug**: `DocumentRepository.create()` commits immediately, so a failure in the enqueue step right after couldn't be rolled back — fixed with an explicit compensating delete.
- **Added `DocumentSplitter.validate_structure()`**: a cheap synchronous readable/non-zero-page check so garbage uploads get an immediate 400 instead of silently queuing.
- **Rule registry regression fixed**: `CrossBranchCodeRule`/`FormatEStampRule` were imported but never registered, and `VisualStampTripartiteRule`/`VisualStampAmcRule` were actively disabled — all to force the rule count to stay at a stale "47" instead of fixing a real duplicate-registration bug. Restored `FormatEStampRule` and the two visual stamp rules (registry is now **50 rules**). **Deliberately did not restore `CrossBranchCodeRule`** — see "Known gaps" below.
- **Real bug in `date_rules.py`**: the new date-presence rules' PASS branch crashed (`AttributeError`) because it treated a `list[str]` as `FieldValue` objects. Fixed and de-duplicated into `_DateRule._evaluate_presence()`.
- Rewrote `test_date_blank_rules.py` (was testing against a broken hand-rolled `RuleContext` double that was never actually exercised) and several other tests that had hardcoded rule counts or premises contradicting real service-layer rules (e.g. "only one active task per application" is enforced by design, not a bug).
- **Fixed genuine Windows flakiness** in `test_bulk_queue.py::test_multiple_worker_processes_claim_disjoint_jobs`: 3 subprocess workers appended to one shared file, which isn't reliably atomic across OS processes on Windows. Fixed by giving each worker its own file and merging in the test. Verified stable across 15+ repeated runs.

### 2026-08-13, later same day: second `.enqueue()` bug + a data-loss incident

While helping the user check on a real document they'd uploaded through the running app, found a **second instance** of the same nonexistent-method bug fixed earlier in `upload/services.py` — this one in `document_processing/services.py::_process_bulk_upload()`, which called `QueueJobRepository.enqueue()` (doesn't exist) instead of `enqueue_uploaded_documents(...)`. Effect: bulk uploads split into per-document records successfully, but those documents were never enqueued for OCR/extraction — the pipeline silently stalled forever with no error surfaced anywhere. Fixed in commit `7f3129d`, with a regression test (`test_bulk_upload_split_documents_are_enqueued_for_processing` in `test_bulk_queue.py`) asserting split documents get queue jobs.

**While verifying that fix, running the new regression test wiped the user's real in-progress application** — see the `isolated_database` warning above. The application, its documents, and its queue job were permanently deleted (hard `DELETE`, no soft-delete/backup). The `users` table was unaffected in that instance (temp account still worked), but don't assume that generalizes — treat any pytest run against a database holding real data as destructive to all of `applications`/`documents`/`queue_jobs`/`users`.

**A third, deeper bug in the same area, fixed same day (commit `36bf456`)**: even with the enqueue bug fixed, every bulk-split document was still guaranteed to fail permanently. `process_one()` correctly refuses to OCR/extract a document without a stored PASS technical-validation report (`document_processing/services.py:214`), but the bulk-split path (`_process_bulk_upload`) never ran technical validation on the documents it created before enqueueing them for that exact processing — the queue worker treats a "skipped, not validated" outcome as a job failure and retries it into permanent `FAILED` status (`app/bulk_queue/workers.py:196-199`). Fixed by calling `TechnicalValidationService(self._db).validate(application_id=application_id)` right after `create_many()` and before `enqueue_uploaded_documents()`, mirroring what the manual (non-bulk) upload flow already does via its own separate `POST .../technical-validation/validate` call. A real application (`#2757`) hit this and burned all its retries — unrecoverable, user had to re-upload.

### 2026-08-14: two more bugs found watching a real 21-page bulk upload process end-to-end (commit `a8c41bf`)

With the three bugs above fixed, a real bulk upload (application `#2758`, a 21-page scanned PDF) was watched through the full pipeline live. It split correctly into 3 documents (Tripartite Agreement, Authority Letter, CNIC Front) and passed technical validation, but hit two more real bugs:

- **`ProcessingMethod.OCR` doesn't exist** (`document_processing/services.py`, `_process_bulk_upload`'s success return) — real member is `PADDLE_OCR`. This crashed *after* the split had already fully succeeded, so the split job was wrongly marked failed and scheduled to redo the entire multi-minute OCR pass on retry (which would then hit the `MAX_COPIES` duplicate guard from the bug above and fail again). Fixed.
- **`PROCESSING_TIMEOUT_SECONDS` was `60.0`** (`document_processing/constants.py`) — but PaddleOCR fallback on this CPU-only machine measured **90–150 seconds per page** in this same session. Any multi-page scanned document (e.g. the 2-page Authority Letter) was mathematically guaranteed to time out. Raised to `600.0`. **If OCR is ever run on a machine without a GPU, re-measure per-page time and adjust this constant** — it's a flat per-document budget, not scaled to page count, so a document with many more pages than this session's test case could still need a higher value.

Verified via a static AST sweep (parse every `.py` file under `app/`, cross-reference every `EnumClass.MEMBER` attribute access against the enum's real `__members__`) that no other enum reference in the codebase points at a nonexistent member, and that every repository method called from `document_processing/services.py` actually exists on its class (including inherited `BaseRepository` methods). Worth re-running this sweep after any future change that references enum members by name.

**Known but not fixed, lower priority**: `_process_claimed_job` in `app/bulk_queue/workers.py` treats a `SKIPPED` processing outcome (e.g. "document did not pass technical validation") identically to a real failure — it retries up to `max_attempts` times even though a technical-validation verdict won't change between retries, wasting time before landing on permanent `FAILED`. Also, running two dev processes (uvicorn + the bulk queue worker) against the same `logs/backend.log` causes harmless but noisy `PermissionError` spam on Windows log rotation (`os.rename` can't rotate a file another process has open) — doesn't affect correctness, just clutters the log.

**Unresolved as of end of 2026-08-14 session**: application `#2758`'s bookkeeping is slightly inconsistent — queue job `#4905` (the split job) and `#4907` (Authority Letter's OCR job) were mid-retry when their worker processes were killed to stop a wasteful redo, so they're stuck showing `PROCESSING` in the DB even though no worker is running. The actual documents/data are fine (3 real documents exist, technically validated). A direct SQL fix was attempted but blocked by an automated command-safety classifier that doesn't respond to in-chat approval (only an actual permission-prompt grant, e.g. via Claude Code's Bash permission settings, would unblock it). **Next session: either grant that permission and run the fix, or just start the queue worker again — `recover_stale_processing` will eventually reclaim both jobs on its own (safe, just means Authority Letter's OCR and the (unnecessary) split job both redo one more time before settling).**

### 2026-08-14: two more real bugs found watching a fresh application (`#2759`) through the full pipeline end-to-end

- **The digital/scanned routing threshold was a flat total, not per-page**: a real CamScanner-exported PDF had its watermark ("CamScanner") embedded as real selectable text on every page — 99 characters across 9 pages — which cleared the old flat 10-character bar despite the actual page content being an untranscribed image. The document was routed as "digital," extracted nothing but watermark noise, and every downstream stage (type detection, field extraction, rule validation) failed. Fixed (commit `812010a`): `MIN_DIGITAL_TEXT_CHARS_PER_PAGE = 40`, checked as an average over the real page count.
- **`PROCESSING_TIMEOUT_SECONDS` (flat 600s, raised from 60s earlier in the day) still wasn't enough**: a real 9-page scan needed ~1000s at this machine's measured 90-150s/page PaddleOCR rate and timed out at the 600s mark. A flat total can never work when real uploads range 1-21+ pages. Fixed (commit `a344a2b`): the deadline is now computed *after* routing, once the real page count is known, as `page_count * PROCESSING_TIMEOUT_SECONDS_PER_PAGE` (180s/page, floored at 180s).
- Both fixes verified against the real file/document, end-to-end, through a full manual pipeline run (`technical-validation/validate` → `process-documents` → `analyze-documents` → `confidence/evaluate` → `normalize` → `validate`) — this confirmed the pipeline stages are **not** automatically chained; each is a separate API call a caller (today: only tests, or a human via curl) must trigger in order. No UI currently drives this chain automatically after upload.
- Note: `/process-documents` reprocesses *every* document on the application, including the raw `BULK_UPLOAD` placeholder alongside its already-split children — redundant OCR work (doubles wall-clock time) but not incorrect, since nothing downstream reads the placeholder's OCR result. ### 2026-08-15: `Application.status` was dead for the whole middle of the lifecycle (foundation audit, Section 1-2 findings)

A full-foundation audit (architecture, data layer, security, etc. — read-only, section by section) found that `ApplicationStatus.PROCESSING` and `ApplicationStatus.PENDING_REVIEW` were **never set anywhere** — grepped every write site: the only place `Application.status` was ever assigned was `human_verification/services.py`'s final-decision submission. Every application showed "Pending" (the `SUBMITTED` label) from creation through OCR, analysis, confidence, normalization and rule validation, and only jumped straight to Approved/Rejected/Corrected once a human decided — `useHumanReview.js`'s status filter, which defaults to `PENDING_REVIEW` (correct design, just aimed at a status nothing produced), silently showed zero applications the entire time.

Fixed: guarded `SUBMITTED → PROCESSING` writes at the three real enqueue call sites (`upload/services.py::upload_bulk()`, `bulk_queue/services.py::enqueue_application()`/`start_processing()`), a `PROCESSING → PENDING_REVIEW` write at the end of a successful `PipelineRunnerService.run()`, and a new terminal status, `PROCESSING_FAILED` (migration `e1f2a3b4c5d6`, chained on `c8d9e0f1a2b3`), written when `_maybe_start_pipeline`'s `PIPELINE_BLOCKED` branch fires (every document failed, so the pipeline never runs — previously this left the application silently stuck at `PROCESSING` forever with no visible sign anything had gone wrong). All writes are guarded to only fire from the expected prior status, so a retried job or a document added after a decision can't regress a status a human has already set. `useHumanReview.js`'s default needed no functional change (it was already correct, just aimed at a status that didn't exist yet) — added a comment explaining the dependency instead. Frontend: `statuses.js` + a new `rose` badge color for `PROCESSING_FAILED`, distinct from `red` (Rejected) and `orange` (Under Review).

Known, accepted limitation carried into this fix, not introduced by it: the guarded writes in `bulk_queue/services.py` read `application` once at the top of the method, before real work (technical validation, job creation) runs, then act on that in-memory value later — the same unprotected read-then-write shape already flagged below for `human_review`/`validation_task`/`validation_run`, not a new category of risk.

Also removed `PROJECT_FULL_CONTEXT.md` (an untracked, 903-line static architecture/API/schema dump that had been sitting in the repo root, never committed). It duplicated ground `README.md` already owns (stack, architecture, DB schema, setup, API surface) and, on comparison, contained claims that were stale or aspirational rather than verified against running code — notably describing the `SUBMITTED → PROCESSING → PENDING_REVIEW → ...` lifecycle above as already-implemented before today's fix actually built it, and describing the `validation` module (see the new known-gap entry directly below) as a normal, integrated pipeline step rather than the disconnected, untriggered module it actually is. Nothing in it was decision-relevant that this file doesn't already cover in more detail and with real dates/evidence.

**`validation` module (ValidationTask/ValidationRun/ValidationLog, Operator Dashboard at `/validation-tasks`) is vestigial, not awaiting integration** — confirmed exhaustively during the same audit: `grep -rl "from app.validation.services import" app` matches only the module's own `routes.py`/`__init__.py`; no scheduler/cron exists anywhere in this codebase; neither benchmark script under `backend/scripts/` references it; the frontend's `createValidationTask` (`services/validation.js`) has zero callers anywhere in the UI. Nothing, anywhere, ever creates a `ValidationTask` in real usage. Three reasons this reads as superseded rather than incomplete: (1) both `ValidationTask` and `ValidationLog`'s own docstrings self-describe as scaffolding for integration that never arrived (*"the unit of work the validation queue hands to an operator **in a later phase**"*, *"the separate User/Operator module will attach the acting operator through **a future migration**"*); (2) `human_verification` already independently and completely implements the same real-world job — an operator reviewing an application's fields, checklist, documents and visual findings, then recording approve/correct/reject — without ever touching `validation`, and it's the module the auto-pipeline (`c3179e1`) actually leads into; (3) the routing history already documented below shows `/human-review` was deliberately repurposed away from this module's Operator Dashboard toward the final-decision screen, demoting the task queue to an un-navigable URL, with no nav entry ever restored. Reconciling the two overlapping designs is a product decision (does a two-stage triage-then-decide workflow across two screens actually get built, or is the one-shot screen the real design), not a code fix — do not wire this module up reactively. Banner comments pointing here were added to `validation/routes.py` and `OperatorDashboardPage.jsx`.

## Known gaps (verified 2026-08-13, don't re-discover from scratch)

**Rule engine coverage vs. `docs/Master_Rules_Combined.md`** — no automated coverage for: blank-date enforcement on Tripartite/Bilateral preambles, PayMin/Digital Muhasil/Paymere BCX terminology matching, organization-name consistency across documents, per-page 1-Link signature requirement, document layout/point-numbering conformance, E-Stamp visual authentication, Notary Public stamp detection, Formal Request Letter subject-line check, CNIC expiry/completeness. (Schedule-of-Charges/BRD signature+stamp checks are deliberately handled via the human-verification manual checklist instead.) **None of these fields have any extraction/normalization support in the codebase today** — confirmed by grep. Do not add a rule for any of them without adding real extraction first: see the `CrossBranchCodeRule` incident above for exactly what goes wrong otherwise (`_CrossDocumentRule` hard-`FAIL`s on a missing field; `_FormatRule` only WARNs; `_VisualRule` degrades to `PENDING_MANUAL_REVIEW` — know which base class before wiring a new rule in).

**Two independent `CRITICAL_FIELDS` lists** (`document_analysis/constants.py`, per-document-type dict, vs `confidence/constants.py`, flat global set) are deliberately different shapes for different purposes — not a bug, now documented in-code.

**Dead-looking but intentionally-kept code**: `DatasetValidationError`, `InvalidReportRequest` — defined, exported, documented in `docs/` as part of their module's exception contract, never raised. Left alone rather than deleted.

**Bulk-splitter and document-analysis use two independent, non-overlapping classifiers (found 2026-08-14, Phase 4 pipeline-orchestration work)** — `app/preprocessing/splitter.py`'s page classifier recognizes the real required-document vocabulary (literal phrases like "TRIPARTITE AGREEMENT", "ACCOUNT MAINTENANCE CERTIFICATE"). `app/document_analysis/extractors.py::detect_document_type`'s classifier recognizes only 4 unrelated categories via its own separate keyword table: bank statement, payslip, ID document, tax document. A document can be split and typed correctly by the first classifier and still fail analysis with "Document type could not be determined" from the second, because the two share no vocabulary. Confirmed directly: a bulk-PDF page containing "TRIPARTITE AGREEMENT" splits cleanly into a `TRIPARTITE_AGREEMENT`-typed document but is permanently unanalyzable — `document_analysis_results` never gets a row for it (see `tests/test_pipeline_orchestration.py`, which had to switch to bank-statement-shaped fixture text to get a real document through analysis at all). **Impact**: any bulk-uploaded application containing non-financial required document types (agreements, letters, certificates — most of the actual checklist) has those documents silently excluded from field extraction and confidence scoring; only a per-document log line (`Document type could not be determined from the extracted text`) records it. Not fixed as part of Phase 4 — pipeline orchestration only chains the four existing post-OCR calls, it doesn't touch either classifier. Needs its own scoping pass: either widen `detect_document_type`'s vocabulary to cover the real required-document checklist, or make `document_analysis` explicitly tolerant of document types it has no extractor for (right now `UnsupportedDocumentType` is a hard per-document failure).

**`validation` module has no actor/reviewer field anywhere (found 2026-08-14, reviewer-identity-from-session work)** — `ValidationTask` and `ValidationLog` (`database/models/validation_task.py`, `database/models/validation_log.py`) record *what* happened (status transitions, field verify/correct/complete/reject actions) but never *who* did it: no `performed_by`/`actor`/`username` column on either model, and none of the module's request schemas (`CompleteRequest`, `RejectRequest`, `RequestCorrectionRequest`, `FieldVerifyRequest`, `FieldCorrectRequest`, `EvidenceReviewRequest` in `validation/schemas.py`) carry one either — confirmed by reading every field on both models and every schema. This is a different shape of gap than the `reviewer_name`/`created_by` issue fixed elsewhere in this same session (`human_verification`, `confidence`, `upload`): those fields *existed* but were spoofable from the request body; here the field doesn't exist at all, so there's no session-swap fix available — closing this needs an actual migration (new column on both tables) plus wiring `current_user` through the module's routes/services the same way, plus backfill/nullability decisions for existing rows. Scoped as its own follow-up, not bundled into the reviewer-identity commit.
